# Session response-ordering repair — September 30, 2026

Status: review reopened; no fix is verified yet. Independent audit of PR #4 at `8a778d5346f10d69e586d0ae46006238e4fd169c` reproduced two real browser defects: a delayed successful refresh from account A overwrites B's refresh cookie after B signs in, and a delayed A logout clears B's cookie. B's access token initially survives the existing JavaScript identity guard, but its next renewal returns 401 and signs it out. Ordinary renewal and account-switch controls pass. The former passing tests did not cover response header ordering.

The current agent read the independent reproducer and created an isolated candidate, bound 184 runtime/test/support files to the saved GitHub source, and is reproducing the final audit before source changes. The original independent run and its fixture-error first attempt remain historical evidence; the final peer run fixes only its favicon proxy route. The peer is publishing an evidence-only branch and will not edit this source lane.

Proposed repair: give each refresh cookie a name bound to the server-generated session ID. Refresh selects only the cookie for the signed access token's session; logout expires only that session's cookie after successful database revocation. A delayed response for A can then change A's cookie without modifying B's cookie. Keep opaque refresh secrets HttpOnly, Secure + __Host- in production, exact-origin checks, atomic rotation/replay control, 15-minute access and eight-hour absolute expiry. Cookie-only anonymous requests must not select or revoke an arbitrary other session. Do not store refresh secrets in JavaScript or use a client identity guard as the cookie-ordering control.

Expected acceptance: hold each old response after actual server processing; perform ordinary sign-out/sign-in in another tab; release the old response; verify new access identity and cookie binding survive, old sessions remain revoked, and new-account renewal succeeds. Test both different-account and same-account new-session cases, forged/missing/duplicate session cookies, production cookie flags, delayed anonymous logout and temporary store failures. Preserve the existing negative controls and normal multi-tab refresh/account/password-reset workflows.

Changes remain in auth/session code and focused verification. Preserve peer engine/booking/calendar runtime, original voice guide and client billing identity. Voice work remains pending. No production provider operations, merge or deployment are authorized by this repair.

Protocol basis: [RFC 6265](https://www.rfc-editor.org/info/rfc6265/) describes races between concurrent Set-Cookie responses and cookie replacement by name/domain/path; [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) documents HttpOnly and host-cookie requirements. Session-specific names are this implementation's remedy, to be verified by real browser response-ordering tests.
